# 0026. 브리프 시그널 요약 문단의 생성 책임과 하루의 시간 범위

- 상태: Accepted
- 날짜: 2026-11-28
- 작성자: jsshin8128

## 맥락

브리프의 시그널 요약 문단은 `signal_digests` 테이블에서 조회하고 있습니다. 그러나 현재는 해당 테이블에 요약 문단을 저장하는 서버 코드가 없어 운영 환경에서는 요약 문단이 항상 비어 있는 상태입니다.

[ADR-0012](0012-brief-signal-digest-backing.md)에서는 요약 문단을 서버 외부에서 생성하여 해당 테이블에 저장하고, 서버는 조회만 담당하도록 결정했습니다. 또한 요약 문단의 기준일을 저장 시각(`created_at`)으로 판단하여, 요약 문단을 생성하는 쪽에서는 한국 시간 기준 하루의 시간 범위를 알 필요가 없도록 했습니다. 민수가 서버 내부의 모듈로 구현되는 시점에 모듈 경계를 후속 ADR에서 결정하기로 했습니다.

이제 서버 내부의 `minsu` 모듈에서 요약 문단을 직접 생성합니다. worker가 시그널을 생성하면서 발행하는 `signal.created` 이벤트를 서버에서 소비하고, 해당 일자의 시그널을 바탕으로 요약 문단을 다시 생성합니다.

이에 따라 ADR-0012의 기존 결정 두 가지를 변경해야 합니다. 서버가 요약 문단을 직접 저장하게 되며, 해당 일자의 시그널을 수집하려면 요약 문단을 생성하는 과정에서도 하루의 시간 범위를 알아야 합니다. 또한 요약 문단은 비동기로 생성하므로 재시도 과정에서 하루의 경계를 넘긴 뒤 저장될 수 있습니다. 기존처럼 저장 시각을 기준으로 날짜를 판단하면 해당 문단이 다음 날 브리프에 표시됩니다.

브리프의 하루 범위는 기획에서 확정한 기준에 따라 MOM-1206에서 한국 시간 오전 6시 이상, 다음 날 오전 6시 미만으로 변경했습니다.

## 결정

**요약 문단의 생성과 저장은 `minsu` 모듈에서 담당하고, 요약 대상 시그널은 `signal` 모듈에서 담당하도록 결정합니다.**

- `signal` 모듈은 `signal.created` 이벤트를 소비하고, 해당 시그널이 속한 프로젝트와 하루의 시간 범위에 해당하는 삭제되지 않은 시그널을 바탕으로 요약 생성에 필요한 입력 데이터를 구성하여 `minsu` 모듈에 생성을 요청합니다. 요약 대상에 포함할 시그널은 해당 데이터를 소유한 모듈에서 결정합니다. 이벤트 소비 위치(offset)는 consumer인 `signal` 모듈에서 관리합니다.
- `minsu` 모듈은 프로젝트와 하루의 시간 범위별로 생성 상태와 최신 요약 문단을 함께 저장합니다. 요약 문단은 사용자가 직접 편집하지 않는 민수의 산출물이므로 생성한 모듈에서 보관합니다. 기능 활성화 여부는 `minsu` 모듈에서 관리합니다.
- 브리프에서는 요청자의 권한을 확인한 뒤 `minsu` 모듈을 통해 요약 문단을 조회합니다. 기존 브리프 API의 응답 형식은 변경하지 않습니다.

**하루의 시간 범위는 `BriefDay`에서 공통으로 정의하고, `BriefDay`를 `signal` 모듈로 옮깁니다.**

요약 생성에 필요한 입력 데이터를 구성하는 `signal` 모듈과 요약 문단을 조회하는 브리프에서 동일한 시간 범위 정의를 사용합니다. 요약 문단을 저장할 때 요약 대상의 시간 범위도 함께 저장하고, 브리프에서는 당일의 시간 범위와 일치하는 요약 문단을 조회합니다.

저장 시각이 아닌 요약 대상의 시간 범위를 기준으로 날짜를 판단하므로, 하루의 경계를 넘긴 뒤 저장된 요약 문단이 다음 날 브리프에 표시되지 않습니다. 시간 범위는 시작 시각과 종료 시각으로 저장하므로 테이블에서는 기존과 마찬가지로 타임존을 별도로 관리할 필요가 없습니다.

**요약 문단 생성은 시그널 생성 흐름과 분리합니다.**

- LLM 호출은 트랜잭션 밖에서 비동기로 실행합니다. 요약 문단 생성에 실패하더라도 시그널 생성과 푸시 알림에는 영향을 주지 않으며, 해당 일자에 직전에 생성한 요약 문단을 유지합니다.
- 동일한 하루의 시간 범위에는 하나의 요약 문단만 유효합니다. 요약 문단을 생성하는 도중 새로운 시그널에 대한 생성 요청이 접수되면, 진행 중인 생성 작업이 끝난 뒤 요약 문단을 한 번 더 생성합니다.
- 하루의 시간 범위가 종료되면 해당 범위의 요약 문단을 새로 생성하지 않습니다. 브리프에서는 당일의 요약 문단만 조회하기 때문입니다.

이번 ADR은 ADR-0012에서 정한 다음 결정을 대체합니다.

- 서버는 `signal_digests` 테이블에 데이터를 저장하지 않습니다.
- `created_at`을 기준으로 요약 문단의 기준일을 판단합니다.
- 요약 문단을 생성하는 쪽에서는 타임존을 알 필요가 없습니다.
- `signal` 모듈이 요약 문단을 소유합니다.
- `BriefDay`를 `mobile` 모듈에 둡니다.

하루의 경계를 `BriefDay`에서 공통으로 정의한다는 결정과 동일한 시간 범위에서 가장 최근에 생성한 요약 문단을 반환한다는 결정은 유지합니다.

## 대안

**`signal` 모듈에서 이벤트 소비, 생성 상태 관리, 비동기 실행, 결과 저장을 모두 담당하는 방안은 채택하지 않았습니다.**

ADR-0012에서 정한 요약 문단의 소유권을 유지할 수 있다는 장점이 있습니다. 그러나 LLM 비동기 생성 작업의 상태 관리 및 재시도 로직이 `minsu`와 `signal` 두 모듈에 중복으로 구현됩니다. [ADR-0015](0015-minsu-async-task-draft-generation.md)에서도 같은 이유로 `signal` 모듈이 비동기 실행까지 담당하는 방안을 채택하지 않았습니다.

**`minsu` 모듈에서 생성한 결과를 `signal` 모듈이 소유한 테이블로 옮기는 방안도 채택하지 않았습니다.**

`signal` 모듈이 이미 `minsu` 모듈에 의존하고 있으므로, 순환 의존을 방지하려면 `minsu` 모듈에서 `signal` 모듈에 생성 결과를 직접 저장할 수 없습니다. 별도의 이벤트를 발행하거나 오케스트레이션 계층을 통해 생성 결과를 전달해야 합니다.

또한 오케스트레이션 모듈은 [ADR-0025](0025-module-boundary-criteria.md)에 따라 자체 테이블을 소유하지 않으므로 이벤트 소비 위치와 생성 상태를 직접 관리할 수 없습니다. 어느 방식을 선택하더라도 동일한 요약 문단이 두 테이블에 중복 저장되며, 요약 문단 생성에는 성공했지만 결과 전달에는 실패할 수 있는 지점이 추가됩니다.

**`created_at`을 기준으로 하루를 구분하는 기존 방식을 유지하는 방안도 채택하지 않았습니다.**

테이블 구조를 변경할 필요가 없다는 장점이 있습니다. 그러나 맥락에서 설명한 것처럼 재시도 과정에서 하루의 경계를 넘긴 뒤 저장된 요약 문단이 다음 날 브리프에 표시될 수 있습니다.

**브리프를 조회할 때 기존 요약 문단이 오래된 경우에만 새로 생성하는 방안도 채택하지 않았습니다.**

브리프 조회가 발생하지 않는 프로젝트에서는 LLM을 호출하지 않아도 된다는 장점이 있습니다. 그러나 푸시 알림을 받고 브리프에 접근한 사용자는 최초 조회 시 갱신되기 전의 요약 문단을 보게 되며, 조회 요청으로 인해 쓰기 작업이 발생합니다.

## 결과

- 시그널이 생성될 때마다 해당 일자의 요약 문단이 갱신됩니다. 운영 환경에서 요약 문단이 표시되는 시점은 worker에서 실제로 시그널을 생성하기 시작한 이후입니다.
- 요약 문단과 시그널 목록은 동일한 하루의 시간 범위 정의를 사용합니다. 하루의 경계를 변경할 때는 `BriefDay`만 수정하면 됩니다.
- 시그널이 접수될 때마다 해당 일자의 시그널 전체를 바탕으로 요약 문단을 다시 생성하므로, 하루 동안 발생하는 LLM 입력 비용은 시그널 수의 제곱에 가깝게 증가할 수 있습니다. 호출 용도별 토큰 사용량 지표를 통해 비용을 모니터링하고, 비용이 증가하면 다음 생성 시각을 늦춰 여러 생성 요청을 한 번에 처리하는 방식으로 개선합니다.
- worker에서 시그널을 소프트 삭제하더라도 별도의 삭제 이벤트가 발행되지 않으므로, 다음 요약 문단 생성 시점까지 기존 문단에 삭제된 시그널의 내용이 남습니다.
- 더 이상 사용하지 않는 `signal_digests` 테이블은 이번 변경 사항이 운영 환경에 배포된 이후 별도 작업으로 삭제합니다. 동일한 배포에서 테이블을 삭제하면 롤링 배포 중 이전 버전의 Pod가 해당 테이블을 조회하면서 브리프 조회에 실패할 수 있기 때문입니다.
- 구현 진행 상황은 MOM-1205와 관련 PR에서 관리합니다.
