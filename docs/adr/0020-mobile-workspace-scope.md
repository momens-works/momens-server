# 0020. 모바일 워크스페이스 범위: bootstrap의 워크스페이스 표현과 선택 소유권

- 상태: Proposed
- 날짜: 2026-08-14
- 작성자: jsshin8128

## 맥락

`GET /api/mobile/bootstrap`은 앱 진입 시 필요한 사용자 정보와 프로젝트 목록을 내려주는 API입니다.

`BootstrapService.load`는 `WorkspaceAccess.listUserMemberships`를 통해 사용자의 멤버십을 한 번 조회하고, 이를
기반으로 workspace id와 role을 매핑합니다. 이후 workspace id 집합을 `ProjectReader.listByWorkspaceIds`에
전달해 프로젝트를 조회하며, 기본 프로젝트는 생성일 기준 가장 최근에 생성된 프로젝트로 선택됩니다.

한편, 응답을 조립하는 과정에서 워크스페이스 정보가 제거되는 문제를 발견했습니다. `BootstrapResponse`는 `me`,
`default_project_id`, `projects` 필드로 구성됩니다. 포함하고, `projects` 는 `id`, `name`, `role` 필드로
구성됩니다. 결과적으로 응답에는 워크스페이스 id 혹은 이름이 존재하지 않습니다.

이로 인해 사용자가 두 개 이상의 워크스페이스에 속한 경우, 서로 다른 워크스페이스의 프로젝트가 하나의 리스트에
담겨 내려오게 됩니다. 클라이언트 입장에서는 각 프로젝트가 어느 워크스페이스에 속하는지 구분할 방법이 없습니다.
또한, 워크스페이스를 전환하는 기능도 구현할 수 없습니다. 현재 앱에서 `workspaceId`는 푸시 payload 전달
과정에만 존재하며, 화면으로 전달된 뒤 사용되지 않고 있습니다.

단, 모바일의 모든 리소스 접근은 공통적으로 "리소스 → 워크스페이스 조회 → 멤버십 검증" 흐름을 따릅니다.

- 태스크는 `TaskReader.workspaceIdOf`로 워크스페이스를 조회합니다.
- 프로젝트는 `ProjectReader.workspaceIdOf`를 워크스페이스를 조회합니다.
- 시그널은 자신이 가진 `workspaceId`로 워크스페이스를 조회합니다.
- 모든 경로에서 `WorkspaceAccess.isMember` 검증이 실패하면 `AUTH_FORBIDDEN`을 반환합니다.

즉, bootstrap의 프로젝트 목록이 사용자가 속한 워크스페이스 집합을 기준으로만 조회되기 때문에, 권한이 없는
프로젝트가 응답에 포함될 가능성은 없습니다.

따라서 이번 이슈는 인가에 대한 결함이 아니라, bootstrap 응답이 각 프로젝트가 어느 워크스페이스에 속하는지를
표현하지 못하는 계약상의 문제입니다.

동작 관점에서는 별도의 고려가 필요합니다.

현재 시점을 기준으로 서버는 워크스페이스 전체 구성원에게 푸시를 발송합니다.

예를 들어, 김민수는 모먼스 워크스페이스에 owner, 다른 프로젝트 워크스페이스에 member로 속해 있고, 앱에는
모먼스의 1차 스프린트가 지정된 프로젝트로 저장돼 있습니다. 다른 프로젝트 워크스페이스의 어떤 프로젝트에서
시그널이 생성됐을 때, 김민수의 기기도 수신자에 포함됩니다. 알림이 뜨고 이를 탭하면 시그널 탭으로 이동합니다.
하지만 앱이 조회하는 경로는 1차 스프린트 프로젝트에 대한 시그널 목록 조회이기 때문에 해당 알림에 대한
시그널은 목록에 노출되지 않는 문제가 발생합니다.

즉, 사용자가 여러 워크스페이스에 속할 경우를 고려하여 동작에 대한 재설계가 필요한 상황입니다.

기획팀에서 워크스페이스 구분이나 전환 방식에 대해 명시적으로 정의된 기록은 아직 없습니다. 모바일 화면
설계서에도 워크스페이스를 전환하는 화면은 존재하지 않습니다.

따라서 이번 ADR에서는 워크스페이스 전환에 대한 기획 결정을 다루지 않습니다. 서버의 계약 관점에서 워크스페이스를
어떻게 표현할지, 그리고 선택된 워크스페이스 상태를 누가 관리할지에 대해서만 결정합니다.

구현 관점에서는 다음과 같은 제약이 존재합니다.

첫째, `BootstrapService`는 멤버십을 한 번만 조회합니다. 두 번 조회할 경우 `READ COMMITTED` 격리 수준상 각
쿼리가 서로 다른 시점의 커밋을 바라보게 됩니다. 이 경우 두 조회 사이에서 멤버십이 변경됐을 때 role을 매칭할
수 없는 프로젝트가 생길 수 있습니다.

둘째, `UserWorkspaceMembership`은 `workspaceId`와 `role` 필드로 구성되며, `ProjectSnapshot`에도 워크스페이스
이름 필드는 포함되어 있지 않습니다.

셋째, `Workspace` 엔티티는 `workspace` 모듈의 `internal` 패키지에 package-private으로 정의되어 있으며, 해당
모듈에는 HTTP 컨트롤러가 존재하지 않습니다. 따라서 bootstrap 응답에 워크스페이스 이름을 포함하려면 새로운
public API를 추가로 구현해야 합니다.

API 계약 관점에서도 다음과 같은 제약이 존재합니다.

ADR-0006에 따라 모든 엔드포인트는 `version = "1"`을 사용하고 있기 때문에 v2로의 분기만 가능합니다. 또한
[API 버저닝 문서](../spec/api-versioning.md)에서는 response body의 필드 삭제, 이름 변경, 타입 변경을 breaking
change로 정의하고 있으며, optional 필드 추가만 non-breaking change로 허용하고 있습니다.

이 규칙이 클라이언트에 미치는 영향은 안드로이드 구현에서 확인할 수 있습니다. 안드로이드는 JSON 파서에서
`ignoreUnknownKeys`를 활성화해 알 수 없는 필드를 무시합니다. 반면 `MobileBootstrapProjectResponse`의 `role`은
기본값이 없는 필수 필드이기 때문에, 해당 값이 누락되면 역직렬화 단계에서 예외가 발생합니다.
kotlinx.serialization 문서에서도 기본값이 없는 프로퍼티는 JSON에서 누락될 경우 예외가 발생하며, 기본값을
지정해야 선택 필드로 처리된다고 명시하고 있습니다.

> Field 'language' is required for type with serial name 'example.exampleClasses04.Project', but it was missing at path: $
> This problem can be fixed by adding a default value to the property, which automatically makes it optional for serialization.

[kotlinx.serialization 기본 직렬화 문서](https://github.com/Kotlin/kotlinx.serialization/blob/master/docs/basic-serialization.md)

이 예외의 영향은 로그인 실패 상황까지 전파됩니다. `SignInRepositoryImpl`은 로그인 이후 bootstrap을 호출하며,
이 호출이 실패하면 저장된 토큰과 DataStore의 Project_Id, avatar_url을 모두 삭제한 뒤 예외를 다시 throw합니다.

세션 갱신 흐름은 다르게 동작합니다. DataStore에 이미 project id가 저장되어 있는 경우 bootstrap을 호출하지
않으며, 호출하더라도 실패를 무시합니다. 따라서 기존 로그인 사용자는 영향이 없지만, 재로그인 시점에는 문제가
발생할 수 있습니다.

배포 상황도 함께 고려해야 합니다. 안드로이드 앱이 데모데이 시연을 위해 팀 구성원 12명의 기기에 설치됐었고
현재는 앱과 연결되어 있던 dev 클러스터가 내려가면서 배포가 중단된 상태입니다. 한편, prod 클러스터는 레거시
서버인 `momens-api`의 요청을 처리하고 있습니다.

prod 환경에서는 신규 서버인 `momens-server`의 Flyway가 비활성화되어 있고, `ddl-auto: validate`입니다. 따라서
엔티티 매핑에 대한 검증만 수행하고 있습니다. [prod 운영 준비 대장](../prod-schema-ledger.md) 기준으로 아직
반영되지 않은 스키마가 16건 존재합니다. 따라서 현재 상태로는 신규 서버를 prod 환경에서 정상 기동할 수
없습니다. 이 작업은 MOM-0840에서 처리할 예정입니다.

어떤 요청이 어느 워크스페이스에 속하는지를 나타내는 방식은 현재 시스템 안에서 몇 가지 패턴으로 나뉘어
있습니다.

웹은 URL의 첫 번째 path segment를 workspace slug로 사용합니다. 구조는 `/{workspace}/projects/{projectId}`
형태이며, 워크스페이스 목록, 설정, 멤버 초대 등도 모두 이 구조를 기반으로 동작합니다.

활성 워크스페이스는 먼저 URL slug를 기준으로 결정됩니다. slug로 조회할 수 없으면 빌트타임 환경변수
VITE_MOMENS_WORKSPACE_ID를 기준으로 사용하고, 그것도 없으면 사용자가 속한 워크스페이스 중 가장 최근에 생성된
것을 기준으로 사용합니다. 마지막으로 조회한 워크스페이스를 별도로 저장하지 않기 때문에, 새로고침 시마다 URL과
멤버십 정보를 기반으로 다시 계산됩니다. 즉, 워크스페이스 선택에 대한 상태는 클라이언트가 관리합니다.

요청이 어느 워크스페이스에 속하는지를 결정하는 방식은 레거시 서버인 `momens-api`에서 두 가지입니다. URL path
parameter로 워크스페이스 id를 직접 받거나, 단건 리소스 API의 경우 리소스 id를 기준으로 워크스페이스 id를
역추적합니다.

이 구조와 관련해 발생할 수 있는 문제 상황이 존재합니다.

현재 태스크 목록은 `tasks.workspace_id`를 기준으로 필터링하지만, 접근 권한을 확인할 때는 `tasks`와 `projects`를
조인해서 `projects.workspace_id`를 다시 조회합니다. 즉, 태스크가 어느 워크스페이스에 속하는지를 판단하는 기준
데이터가 두 군데에 나뉘어 있는 구조입니다. 그리고 이 두 값의 일치를 강제하는 제약은 없습니다.

일반적인 제품 기능 관점에서 보면 프로젝트를 다른 워크스페이스로 이동하는 경우는 흔하지 않습니다. 레거시 코드의
`UPDATE projects` 구문에는 `workspace_id`가 포함되어 있지 않아서, 애플리케이션 기능만으로 프로젝트를 다른
워크스페이스로 옮길 수 없습니다. 태스크 생성 시에도 `WorkspaceForProject`에서 조회한 워크스페이스 값을
`tasks.workspace_id`에 저장하는 구조입니다.

따라서 두 값이 어긋날 수 있는 상황은 애플리케이션 외부에 있습니다. 개발자가 시드 데이터 삽입 등 수동으로 행을
생성하는 작업이 여기에 해당합니다.

두 값이 어긋나면 태스크 목록 조회 결과와 접근 제어 결과가 서로 달라질 수 있습니다. 예를 들어 에브리타임
클론코딩 프로젝트의 소속 워크스페이스가 솦트에서 모먼스로 변경되었지만, 해당 프로젝트에 속한 태스크의
`tasks.workspace_id`는 여전히 솦트를 가리키고 있다고 가정합니다.

이 경우 신진수가 모먼스 워크스페이스의 태스크 목록을 조회하면 `게시글 목록 조회 API 구현` 태스크는 보이지
않습니다. 목록 조회가 `tasks.workspace_id` 기준으로 필터링되기 때문입니다. 반대로 해당 태스크를 링크로 직접
열면 접근 제어는 `projects.workspace_id`를 기준으로 모먼스 소속으로 판단되기 때문에 정상적으로 응답이
내려옵니다. 결과적으로 목록에는 없지만 직접 접근은 가능한 상태가 됩니다.

신진수는 모먼스와 솦트 워크스페이스에 모두 속해 있으므로 이 상황에서 접근 자체에는 문제가 없습니다. 하지만
솦트에만 속한 팀원의 경우에는 반대로 동작합니다. 솦트 태스크 목록에서는 해당 태스크가 보이지만, 상세 화면을
열면 접근 제어에 의해 `403 Forbidden`이 발생합니다.

현재까지 이런 문제가 실제로 발생했다는 기록은 확인되지 않았습니다. 하지만 DB 레벨에서 `tasks.workspace_id`와
`projects.workspace_id`의 일치를 보장하지 않기 때문에, 프로젝트의 소속 워크스페이스를 변경하는 작업이 생길
경우 두 값을 함께 갱신하는 책임은 개발자가 져야합니다.

MCP는 URL이 없는 환경이기 때문에 다른 방식을 사용합니다. 동의 화면에서 워크스페이스를 하나 선택하도록 하고,
선택된 값을 access token에 포함합니다. 하나의 grant는 하나의 워크스페이스에 바인딩되며, 다른 워크스페이스를
사용하려면 재동의가 필요합니다.

외부 제품 사례도 참고했습니다.

Linear는 워크스페이스를 최상위 컨테이너로 두고 그 아래에 team, project, issue를 배치합니다.

> A Linear workspace is the container for all issues, teams and other concepts relating to an individual company.

[Linear 개념 모델 문서](https://linear.app/docs/conceptual-model)

Linear는 각 team 단위 프로젝트 페이지와 workspace 단위 프로젝트 페이지를 모두 제공해 전체 프로젝트를 한
화면에서 조회할 수 있도록 구성되어 있습니다. 프로젝트는 여러 team에 공유될 수 있지만 issue는 하나의 project에만
속합니다.

[Jira Cloud Android site 전환 문서](https://support.atlassian.com/jira-cloud-android/docs/switch-between-your-jira-sites/)

Jira는 site를 조직 단위로 사용하며, 모바일에서는 여러 site를 사용하는 경우 계정 아바타를 통해 명시적으로 site를
전환하는 구조입니다.

푸시 알림에 대한 진입 경로도 고려해야 합니다. FCM에서는 notification payload와 data payload를 함께 보낸 경우
앱이 background 상태일 때 `onMessageReceived`가 호출되지 않습니다.

> the notification is delivered to the device's system tray, and the data payload is delivered in the extras of the intent of your launcher Activity

[FCM Android 메시지 수신 문서](https://firebase.google.com/docs/cloud-messaging/android/receive-messages)

즉, 사용자가 알림을 클릭해 앱이 실행된 이후 시점에 payload를 기반으로 진입 경로를 결정할 수 있습니다. 서버는
push data에 `notification_type`, `destination`, `signal_id`, `project_id`, `workspace_id` 필드를 포함하고
있으며, 앱도 이를 intent extras에 포함하여 전달하고 있습니다. 하지만 화면 이동 로직에서는 `destination`과
`signal_id`만 사용하고 `workspace_id`는 활용되지 않고 있습니다.

이번 ADR에서는 다음 항목을 결정합니다.

1. bootstrap 응답에서 워크스페이스를 어떻게 표현할지
2. `projects[].role`의 위치 및 구조
3. response 필드 변경에 대한 breaking change 처리 방식
4. 선택된 워크스페이스 상태의 소유 주체 및 저장 위치
5. request에서 워크스페이스 범위를 명시적으로 받을지 여부
6. 푸시 알림 진입 시 워크스페이스 전환 방식
7. 워크스페이스 이름 조회 책임을 가져가는 모듈 경계
8. bootstrap 응답이 보장해야 하는 불변 조건

## 결정

이 문서에서 다루는 내용은 두 범주로 나뉜다. 아래 결정 1부터 3까지는 서버에서 독립적으로 판단할 수 있는
범위이므로 이번 문서에서 확정한다. 나머지는 bootstrap 응답 계약에 해당하며, 레거시 웹 이관이 완료된 이후에
다시 검토한다. 해당 내용은 지금까지 조사한 결과와 함께 `이관 이후 결정할 사항` 절로 옮겼다.

결정 번호는 이번 문서의 확정 범위를 기준으로 다시 부여했다. 초안의 결정 4, 5, 6은 각각 결정 1, 2, 3으로
변경했다. 보류한 초안의 결정 1, 2, 3, 7, 8은 추적이 가능하도록 기존 번호를 유지했다.

워크스페이스 선택 상태와 전환은 클라이언트가 관리한다. 서버는 각 요청이 속한 워크스페이스와 해당 사용자의
권한을 검증한다. 기존 인가 경로와 푸시 payload는 변경하지 않는다.

### 1. 선택된 워크스페이스는 클라이언트가 로컬에 저장하고 서버는 보관하지 않는다

ADR-0003은 access token의 클레임을 사용자를 식별하는 `sub`로 최소화하고, 전송 수단에 관한 정보를 포함하지
않도록 결정했다. 워크스페이스를 토큰에 넣으면 이 원칙과 충돌하며, 워크스페이스를 전환할 때마다 토큰을 다시
발급해야 한다.

MCP의 사례가 이미 이 부분에 대한 비용이 존재함을 보여준다. URL을 사용할 수 없어 토큰에 워크스페이스를 포함했기
때문에 하나의 그랜트가 하나의 워크스페이스에 바인딩되었고, 다른 워크스페이스로 전환하려면 다시 동의해야 한다.

웹은 다른 방식을 사용한다. 워크스페이스 선택에 대한 상태는 URL에 위치한다. 서버는 이를 기억하지 않는다.
새로고침할 때마다 URL과 워크스페이스 목록을 바탕으로 활성 워크스페이스를 결정한다. 모바일에는 URL이 없으므로
로컬 저장소가 같은 역할을 맡는다.

서버가 마지막 워크스페이스 선택에 대한 상태를 저장하려면 새로운 테이블과 쓰기 API가 필요하다. 읽기 전용인
bootstrap에서 쓰기가 발생하며, 여러 기기 간 선택 상태를 어떻게 동기화할지에 대해서도 추가적인 설계가
필요해진다.

이 결정으로 기존 인가 코드는 변경하지 않는다.

### 2. 요청에서 workspace_id를 전달 받지 않는다

`projects.workspace_id`에는 `NOT NULL` 제약이 걸려 있으므로, 하나의 프로젝트 ID만로 해당 프로젝트가 속한
워크스페이스를 결정할 수 있다.

요청에서 `workspace_id`와 프로젝트 ID를 함께 전달받는 경우, 서버는 매 요청마다 두 값이 일치하는지 검증해야
한다. 또한 값이 불일치할 때의 응답도 별도로 정의해야 한다.

한편, 정상적인 사용자 흐름에서는 두 값이 서로 어긋날 일이 없다. 이러한 불일치는 클라이언트 결함이 있는 경우에
발생한다. 사용자가 권한이 없는 워크스페이스의 프로젝트 ID를 전달하는 경우 역시 기존 멤버십 검증 단계에서 이미
차단된다. 앞서 맥락 절에서 살펴본 `tasks.workspace_id` 사례는 동일한 값을 두 곳에서 관리할 때 발생하는 비용을
설명하고 있다.

이 결정은 ADR-0012를 변경하는 것이 아니다. ADR-0012는 서버가 소유하지 않는 테이블에 `workspace_id`를 함께
저장하여, 멤버십 검사와 별개로 쿼리 단계에서도 다른 워크스페이스의 데이터가 노출되지 않도록 하는 관례를
정의한다. 해당 방어 로직은 서버 내부 쿼리 수준에서 적용되는 것이며, 이번 결정은 이 값을 클라이언트 요청에서
중복으로 받지 않겠다는 의미이다.

따라서 [에러 코드](../spec/api-response-error-codes.md)에 예시로만 정의되어 있는 `WORKSPACE_NOT_FOUND` 역시
이번 작업에서는 구현하지 않는다. 해당 에러는 워크스페이스를 직접 다루는 화면이 추가되는 시점에 다시 검토한다.

### 3. 푸시 알림으로 진입할 때 앱이 bootstrap 목록과 대조해 워크스페이스를 전환하며, 서버의 payload는 변경하지 않는다

서버는 현재 푸시 data에 `workspace_id`를 포함하고 있다. 하지만 이를 읽는 로직이 없어 활용되고 있지 않는
상태이다. 초안 결정 1에 따라 앱이 워크스페이스 목록을 가지게 될 경우, 기존 payload의 값을 활용할 수 있다.

payload에 워크스페이스 이름이나 진입 가능 여부는 추가하지 않는다. 해당 정보는 푸시 발송 시점의 스냅샷이므로
사용자가 알림을 누르는 시점의 상태와 다를 수 있다. 최종 접근 가능 여부는 상세 조회 API가 현재 멤버십을 기준으로
다시 판단한다.

워크스페이스 전환 여부를 사용자에게 다시 묻지 않는다. 알림 문구에 프로젝트 이름이 포함되므로 사용자가 알림을
누른 행위 자체를 해당 프로젝트로 이동하겠다는 의사 표현으로 간주한다.

payload의 `workspace_id`가 현재 bootstrap 목록에 없으면 bootstrap을 한 번 더 조회한다. bootstrap은 읽기 전용
트랜잭션이므로 반복 호출해도 안전하다. 재조회 이후에도 해당 워크스페이스가 없으면 현재 멤버십이 없는 것으로
판단하고 진입하지 않는다.

하지만 아무런 안내 없이 흐름을 종료해서는 안 된다. 사용자가 알림을 눌렀는데 화면이 그대로라면 애플리케이션
결함으로 인식할 수 있지만, 실제로는 권한이 회수된 정상적인 상태일 수 있다. 클라이언트는 사용자에게 안내 표시를
하는 방식 등의 검토를 해볼 수 있다.

앱에서 수행하는 이 대조는 진입할 화면을 결정하기 위한 사전 판단이며, 인가가 아니다. 최종 인가는
`GET /api/mobile/signals/{signalId}`가 요청마다 현재 멤버십을 기준으로 수행한다.

## 이관 이후 결정할 사항

현재 검토 중인 방향은 bootstrap 응답에 워크스페이스 정보를 추가하는 것이다. 아래 항목은 모두 해당 응답 계약과
관련된 내용이다. 현재 bootstrap은 앱잼 데모를 위해 하나의 워크스페이스에 종속된 형태로 구현한 임시
요구사항이다. 이 계약은 레거시 웹 이관이 완료된 이후에 다시 검토한다. 다만 이관 과정에서 워크스페이스
범위와 관련된 문제가 확인되면 해당 시점에 함께 검토한다.

기본 워크스페이스와 기본 프로젝트를 선정하는 기준이 아직 확정되지 않았으며, 워크스페이스 전환 화면도 설계되지
않았다. 따라서 이번 문서에서는 결론을 확정하지 않고, 지금까지 조사한 내용과 판단에 필요한 근거만 남긴다.

각 항목의 번호는 초안과의 대응 관계를 추적할 수 있도록 기존 번호를 유지한다. `대안` 절과 `결과` 절에도 아래
항목을 검토하며 확인한 내용이 함께 포함되어 있다.

### 초안 결정 1. 응답에 `workspaces` 배열을 추가하고 `projects`는 구조를 유지한다

`projects.workspace_id`가 `NOT NULL`이므로 클라이언트는 `workspace_id`를 기준으로 프로젝트 목록을 묶을 수 있다.
반대로 응답을 워크스페이스별 중첩 구조로 변경하면 기본 프로젝트 선정 규칙을 워크스페이스마다 다시 정의해야
한다. 또한 안드로이드의 `ignoreUnknownKeys`는 새로운 필드가 추가되는 경우에는 호환성을 보장하지만, 배열 구조가
바뀔 경우 타입 불일치로 인해 예외를 발생시킨다.

응답에는 `default_workspace_id`를 추가한다. 프로젝트가 하나도 없는 워크스페이스에 멤버로 초대만 받은 상태가
성립할 수 있으며, 현재 계약도 프로젝트가 0개인 경우 정상 응답인 200을 반환한다. 프로젝트 존재 여부와 관계없이
최초 진입할 워크스페이스를 결정할 수 있어야 클라이언트가 화면을 구성할 수 있다.

응답 형식은 다음과 같다.

```json
{
  "me": {
    "id": "0b3f8c1a-2d4e-4f6a-8b9c-1e2d3f4a5b6c",
    "email": "minsu@example.com",
    "name": "김민수",
    "avatar_url": null
  },
  "default_workspace_id": "8f2b1c40-3a55-4d21-9c07-6ab19d3f5e88",
  "default_project_id": "30d9e9fe-f43b-4097-a88e-dc19f0a5b025",
  "workspaces": [
    {
      "id": "8f2b1c40-3a55-4d21-9c07-6ab19d3f5e88",
      "name": "모먼스",
      "role": "owner"
    }
  ],
  "projects": [
    {
      "id": "30d9e9fe-f43b-4097-a88e-dc19f0a5b025",
      "workspace_id": "8f2b1c40-3a55-4d21-9c07-6ab19d3f5e88",
      "name": "Q2 Activation Readiness"
    }
  ]
}
```

워크스페이스별로 프로젝트를 묶는 순서와 화면에 표시하는 방식은 제품 정책이므로 서버 계약에서 정하지 않는다.
`projects`의 정렬은 기존과 동일하게 생성 시각 내림차순을 유지한다.

### 초안 결정 2. `role`은 `workspaces`로 옮기고 `projects`에서는 제거한다

`role` 값은 `workspace_members` 테이블에만 존재한다. 이 사실은 코드와 문서 세 곳에 명시되어 있다.

- `ProjectSnapshot`은 "멤버 role은 workspace 멤버십에서 관리하므로 여기 두지 않습니다"라고 설명한다.
- [모바일 API](../spec/mobile-api.md)는 "`role`은 소속 workspace 멤버십 role입니다"라고 정의한다.
- [모바일 MVP 서버 요구사항](../design/mobile-mvp-server-requirements.md)은 "별도 project 멤버 테이블 없이 소속
  workspace 멤버십 role로 매핑한다"고 정한다.

현재 `projects[].role`은 프로젝트의 속성처럼 보이지만 실제로는 워크스페이스 멤버십의 값을 프로젝트 수만큼
복제한 것이다. 응답에 워크스페이스가 추가되면 이 값을 프로젝트마다 반복할 이유가 없다.

동일한 값을 두 곳에 남길 이유가 없으므로, `role`은 `workspaces`로 옮기고 `projects`에서는 제거한다.

### 초안 결정 3. `projects[].role` 제거는 breaking change이지만 v2로 선언하지 않고 배포로 처리한다

[API 버저닝](../spec/api-versioning.md)은 response body의 필드 삭제를 breaking change로 규정한다. 이번
결정에서도 이 기준은 변경하지 않는다.

prod 클러스터에는 `momens-server`가 이미 배포되어 있으며 `/api` 경로로 들어오는 요청을 처리하고 있다. 하지만
현재 배포된 빌드는 2026-07-10 시점의 버전으로, 이번 계약이 구현되기 전의 상태다. 이후 추가된 마이그레이션도
prod 클러스터에 반영되지 않아 최신 빌드는 매핑 검증 단계에서 기동하지 못한다. 앱 역시 dev 클러스터에서 시연한
뒤 배포가 중단되어 현재 이 응답을 소비하는 클라이언트는 없다. 이 상황에서 v2를 추가하면 실제 소비자가 없는
v1을 불필요하게 계속 유지해야 한다.

그렇더라도 필드 삭제에 따른 비용은 존재한다. 안드로이드에서 `role`은 기본값이 없는 필수 프로퍼티이므로 응답에서
누락되면 파싱 단계에서 예외가 발생한다. 앞서 설명 한 것 처럼 `SignInRepositoryImpl`은 로그인 직후 bootstrap
호출이 실패하면 토큰을 삭제하고 예외를 다시 던지므로 신규 로그인이 전부 실패하게 된다. 반면 세션 갱신
경로에서는 실패를 무시하므로 기존 로그인 사용자에게는 증상이 나타나지 않다가 재로그인 시점에 문제가 발생한다.

따라서 배포는 다음 세 단계로 나누어 반영한다.

1. 서버가 `workspaces`, `default_workspace_id`, `projects[].workspace_id`를 추가하되 `projects[].role`은
   유지한다.
2. 앱이 `workspaces`를 사용하도록 변경하고 `projects[].role`에 대한 의존을 제거한다.
3. 서버가 `projects[].role`을 제거한다.

### 초안 결정 7. 워크스페이스 이름은 `workspace` 모듈 root에 `WorkspaceReader`를 공개해 조회한다

`Workspace` 엔티티는 `workspace` 모듈의 `internal` 패키지에 package-private으로 선언되어 있다. 다른 모듈은
`workspace`의 public API만 사용할 수 있다.

모듈 root에 인터페이스를 두고 구현을 `internal`에 배치하는 방식이 이 경계를 유지하는 구조이다.

> `workspace` 모듈의 공개 계약은 MOM-0894에서 하위 도메인별 named interface로 이동했습니다. `WorkspaceReader`는 `core` 패키지에 있고, 구현은 `core/internal` 패키지에 있습니다. 이 문서는 2026-08-14 시점의 기록이므로 본문은 수정하지 않았습니다.

공개 계약은 다음과 같이 정의한다.

- `WorkspaceReader.listByIds(Collection<UUID>)`
- 반환 타입: `List<WorkspaceSnapshot>`
- `WorkspaceSnapshot`의 필드: `id`, `name`

Spring Modulith는 모듈의 public API를 패키지와 접근 제어자를 기준으로 정의하며 타입 이름에 관한 규칙은 두지
않는다. 따라서 네이밍에 대한 근거는 이 레포지토리의 기존 관례를 따른다.

모듈 root에 있는 조회 전용 public API 8개는 모두 `Reader`라는 이름을 사용하며, 복수 결과를 반환하는 메서드는
`list`로 시작한다. 반환 타입에 `Snapshot`을 사용하는 이유는 bootstrap이 `ProjectReader.listByWorkspaceIds`와
같은 위치에서 이 조회를 호출하기 때문이다.

워크스페이스 이름을 멤버십 조회 결과에 포함하지 않는다. 멤버십은 nested module인 `access`가 소유하고,
워크스페이스는 `internal`이 소유한다. `access`가 `workspaces`를 조인하면 nested module이 root의 `internal`을
참조하게 된다. 반대로 `internal`이 `workspace_members`를 조회하면 root가 nested module을 참조하게 된다.
`access`의 `package-info`도 이 하위 도메인을 외부에 root의 `WorkspaceAccess`를 통해서만 공개한다고 명시한다.

이 결정으로 조회가 한 번 추가되지만, PR #42에서 방지한 경합이 다시 발생하지는 않는다. 해당 주석에서 다루는
문제는 `role`이 누락되는 상황이며, `role`은 한 번의 멤버십 조회 결과에서만 가져온다. 추가로 조회하는 워크스페이스
이름은 권한 판정에 사용되지 않으므로 경합에 영향을 주지 않는다.

`workspace` 모듈에는 HTTP 컨트롤러를 추가하지 않는다. `/api/mobile/*` API는 `mobile` 모듈이 소유한다는 기존
경계를 유지한다.

> `WorkspaceAccess`와 `WorkspaceRoleReader`는 MOM-0885에서 `WorkspaceMembershipReader` 하나로 통합했다. 이 문서는 2026-08-14 시점의 기록이므로 본문은 수정하지 않았다.

### 초안 결정 8. bootstrap 응답이 보장해야 하는 불변식을 계약으로 명시한다

결정 3에서 앱이 수행하는 워크스페이스 대조는 하나의 bootstrap 응답 안에서 워크스페이스와 프로젝트의 관계가
일관된 경우에만 성립한다. 이는 구현 세부 사항이 아니라 클라이언트가 의존하는 계약이므로 다음 불변식을
명시한다.

- 모든 `projects[].workspace_id`는 `workspaces` 배열에 포함되어야 한다.
- `default_project_id`가 `null`이 아니라면 해당 프로젝트는 `projects` 배열에 포함되어야 하며, 프로젝트의
  `workspace_id`는 `default_workspace_id`와 일치해야 한다.
- 멤버십을 한 번 조회해 확정한 workspace ID 집합을 워크스페이스 이름 조회와 프로젝트 조회에 동일하게 전달해야
  한다.

세 번째 항목은 앞의 두 불변식을 보장하기 위한 구현 규칙이다. 전체 조회가 세 번 수행되더라도 이후 두 조회에
동일한 workspace ID 집합을 전달하면, 조회 사이에 멤버십이 변경되더라도 하나의 응답 안에서는 서로 일관된 값을
조립할 수 있다.

## 대안

- **`projects`를 워크스페이스 단위로 중첩한다.**

  응답 구조만으로 프로젝트의 소속 워크스페이스가 드러나기 때문에, 앱에서 별도로 목록을 묶는 로직이 필요 없다.
  하지만 기본 프로젝트를 선택하는 규칙을 워크스페이스별로 다시 정의해야 한다. 또한 안드로이드의
  `ignoreUnknownKeys`는 필드 추가 정도에 한하여 안전하게 처리할 뿐, 배열 구조가 바뀌는 경우는 예외가 발생한다.
  결과적으로 영향 범위가 단일 필드가 아니라 응답 전체로 확대된다.

- **워크스페이스를 먼저 선택하는 2단계 진입 구조를 도입한다.**

  먼저 워크스페이스 목록을 조회하고, 그중 하나를 선택한 뒤 해당 워크스페이스의 프로젝트를 조회하는 방식이다.
  웹과 레거시 서버의 라우팅 구조와 유사하다. 하지만 앱 진입 시 네트워크 왕복이 두 번으로 늘어나고, 워크스페이스가
  하나뿐인 사용자에게도 선택 단계를 강제하게 된다.

- **액세스 토큰에 `workspace_id`를 포함한다.**

  토큰만으로 요청의 워크스페이스 범위를 확정할 수 있다. 하지만 ADR-0003에서 정의한 최소 클레임 원칙과 충돌한다.
  MCP에서도 워크스페이스 전환 시 재동의가 필요해지는 비용을 이미 확인했으며, 앱에서는 이 비용이 재로그인으로
  이어진다.

- **서버에 마지막 선택 워크스페이스를 저장한다.**

  사용자가 기기를 변경해도 마지막 선택 상태를 유지할 수 있다. 그러나 이를 위해 새로운 테이블과 쓰기 경로가
  필요하고, 현재 읽기 전용인 bootstrap에서 쓰기 작업이 발생하게 된다. 또한 웹은 워크스페이스 선택 상태를 저장하지
  않고 있다. 따라서 웹과 기준이 달라진다.

- **`workspace_id`를 쿼리 파라미터 또는 헤더로 전달한다.**

  서버가 클라이언트 요청의 워크스페이스 범위를 한 번 더 검증할 수 있다. 하지만 프로젝트 id만으로도 워크스페이스가
  유일하게 결정되기 때문에, 두 값의 일치 여부를 추가로 검사해야 하고 불일치 케이스에 대한 전용 응답도 새로
  정의해야 한다. 이러한 불일치는 정상적인 사용자 흐름에서는 발생하지 않으며, 사실상 클라이언트 오류에서만
  발생한다.

- **v2 엔드포인트를 추가해 `role` 제거를 처리한다.**

  ADR-0006 기준에 가장 정합적인 방식이며, breaking change 여부를 별도로 검토할 필요가 없다. 하지만 v1을 계속
  유지해야 한다. 현재 배포 상황에서는 불필요한 선택이다.

- **`projects[].role`을 유지하면서 `workspaces[].role`을 추가한다.**

  기존 필드를 제거하지 않으므로 배포 순서에 제약이 생기지 않는다. 다만 같은 의미의 값이 두 곳에 남게 된다. 현재
  코드와 문서는 모두 `role`의 소유자를 워크스페이스 멤버십으로 정의하고 있다. 이런 상황에서 중복 구조를 유지하면
  두 값이 서로 어긋날 가능성까지 API 계약으로 고착화할 위험이 있다.

- **`workspaces`에 `slug`를 함께 제공한다.**

  웹 URL 구조와 일치하며 향후 딥링크에도 활용할 수 있다. 하지만 현재 앱에는 URL 기반 라우팅이 없기 때문에 사용할
  곳이 없다. 필드 추가는 하위 호환성에 문제가 없기 때문에, 딥링크가 도입되는 시점에 다시 검토하는 것이 적절하다.

- **푸시 payload에 워크스페이스 이름 또는 접근 가능 여부를 포함한다.**

  앱이 bootstrap을 조회하지 않고도 화면을 구성할 수 있다. 하지만 해당 값은 푸시 발송 시점의 스냅샷이기 때문에,
  사용자가 알림을 클릭하는 시점의 상태와 달라질 수 있다. 최종 접근 가능 여부는 상세 조회 API가 현재 멤버십
  기준으로 판단한다.

- **워크스페이스를 앱에 노출하지 않고 서버가 하나를 고정 선택한다.**

  기존 화면을 변경하지 않아도 되는 가장 단순한 방식이다. 하지만 현재 문제를 해결하는 것이 아니라 유지하는
  접근이다. 서버가 선택한 워크스페이스를 앱에서 변경할 수 없기 때문에, 다른 워크스페이스에서 발생한 푸시는 계속
  열 수 없는 상태가 된다.

## 결과

- 두 개 이상의 워크스페이스에 속한 사용자가 각 프로젝트의 소속을 구분하고 워크스페이스를 전환할 수 있다.

- `role`의 소유 구조가 워크스페이스 멤버십 하나로 정리되면서 동일 값이 프로젝트 수만큼 반복되지 않는다.

- 서버에 새로운 상태를 추가하지 않는다. 신규 테이블이나 쓰기 경로 없이 기존 bootstrap은 읽기 전용으로 유지된다.

- 기존 인가 경로는 변경하지 않는다. 리소스에서 워크스페이스를 찾고 멤버십을 확인하는 현재 흐름을 유지한다.

- 새로운 에러 코드는 추가하지 않는다. 예시로 존재하던 `WORKSPACE_NOT_FOUND`도 이번 범위에서는 구현하지 않는다.

- 앱까지 전달되었지만 사용되지 않던 푸시 payload의 `workspace_id`를 실제 활용한다. 서버 payload 구조는 변경하지
  않는다.

- `projects[].role` 제거는 [API 버저닝](../spec/api-versioning.md) 기준상 breaking change에 해당한다. 이번
  결정은 해당 기준을 변경하는 것이 아니라, 현재 연결된 클라이언트가 없기 때문에 v2 도입에 대해 실익이 없다고
  판단한 것이다.

- 두 레포지토리의 배포 순서를 반드시 맞춰야 한다. 순서가 어긋나면 로그인이 실패하게 된다.

- 선택한 워크스페이스는 기기에 저장되므로 기기마다 값이 달라질 수 있고, 앱을 재설치하면 기본값으로 초기화된다.

- 멤버십이 회수되더라도 로컬에 저장된 워크스페이스 선택 상태가 즉시 무효화되지는 않는다. 해당 상태는 다음
  bootstrap 호출 시점이나 최초로 `403 Forbidden` 응답을 받은 시점에 정리된다. 이는 ADR-0003에서 정의한 것처럼,
  access token의 유효기간 내에 발생한 권한 변경이 일정한 시차를 두고 반영되는 모델과 유사하다.

- bootstrap의 DB 조회가 두 번에서 세 번으로 증가한다. 모든 조회는 단일 읽기 전용 트랜잭션 내에서 수행되며 id
  집합 기반 조회로 처리된다.

- 워크스페이스가 하나뿐인 사용자는 응답 크기만 증가하고 화면 동작은 유지된다.

- MOM-0846에서 서버 구현과 함께 [모바일 API](../spec/mobile-api.md)의 앱 진입 관련 절과
  [모듈 맵](../design/module-map.md)의 `workspace`, `mobile` 항목을 함께 갱신한다.

- 안드로이드에서는 별도 작업으로 응답 파싱, 워크스페이스 목록 저장, 전환 진입점, 푸시 진입 처리를 구현한다. 현재
  앱은 기본 프로젝트 id 하나만 저장하고 있으며 프로젝트 목록을 처리하는 로직이 없다.

- 현재 푸시는 소비 시점 기준으로 워크스페이스 전체 구성원에게 발송되며 프로젝트 단위 필터가 없다. 따라서 사용자가
  여러 워크스페이스에 속한 경우 실제로 보지 않는 프로젝트 알림까지 수신할 수 있다.

  외부 제품들은 일반적으로 리소스와 사용자 간 관계를 기준으로 알림 대상을 제한한다. Linear는 이슈를 생성했거나,
  담당자로 지정되었거나, 멘션된 사용자를 자동으로 구독자로 처리하고, 구독 여부에 따라 알림 수신이 결정된다.

  > Subscribing to an issue determines whether notifications are received for that issue, based on notification preferences.

  [Linear 알림 문서](https://linear.app/docs/notifications)

  Jira는 watcher, 담당자, 보고자를 기본 수신 대상으로 사용하며, 모바일 앱에서는 site 단위로 알림 채널을 분리해 각
  site별로 알림을 개별 제어할 수 있다.

  하지만 모먼스의 시그널은 사용자가 생성한 이슈가 아니라 외부에서 감지된 이벤트이기 때문에 생성자나 담당자를 구독
  기준으로 사용할 수 없다. 알림 수신 범위는 제품 정책 영역이므로 이번 결정과 분리해 별도 과제로 다룬다.

- 워크스페이스 전환 화면과 설정 화면은 현재 화면 설계에 포함되어 있지 않다. 3탭 공통 헤더에는 로고와 프로필만
  존재하며, 프로필에는 별도 동작이 정의되어 있지 않다. 전환 진입 위치는 기획과 별도로 확정한다.

- `teams` 레포지토리에는 워크스페이스 범위에 대한 결정 기록이 없고, 용어집에서도 Workspace를 아직 구현되지 않은
  상위 개념으로 정의하고 있다. 이번 결정은 기획과 공유하고 용어집 반영 여부를 논의한다.

- 워크스페이스 범위를 입력으로 받는 조회 API와 `WORKSPACE_NOT_FOUND` 에러는 설정 화면 또는 멤버 화면이 추가되는
  시점에 다시 검토한다.

- 웹은 slug를 URL에 사용하지만 앱에서는 사용하지 않는다. 향후 딥링크가 도입되면 `workspaces` 응답에 slug를
  포함할지 다시 판단한다.

- 워크스페이스 멤버십의 `role`과 태스크의 `role`이 같은 이름을 사용하고 있어, 두 필드의 이름을 구분할지
  검토했다. 그러나 응답 필드 이름 변경은 [API 버저닝](../spec/api-versioning.md) 기준상 필드 삭제와 동일한
  breaking change에 해당하므로 이번 범위에서는 제외한다. 멤버십 `role`은 레거시에서 이미 `owner`, `admin`,
  `member`로 사용하고 있으며 웹 이관 계약과도 연결되어 있어 이번 결정에서 단독으로 변경할 수 없다. 반면 태스크
  `role`은 레거시에 없는 값이므로 이름을 변경한다면 이쪽을 건드려야 한다. 하지만 새 이름은 팀에서 공통으로
  사용하는 용어여야 하므로 용어집에 먼저 반영한 뒤 확정한다. 이번에는 기존 계약을 유지하고, 모바일 API 명세와
  코드 설명에서 두 `role`의 의미를 명확히 구분하는 수준까지만 반영한다.

- 모바일 bootstrap처럼 레거시에 동일한 endpoint가 없는 신규 API에 대하여 이관 전략의 응답 형식 분류에 어떻게
  적용할지 확인이 필요하다. 이관 전략에서는 각 endpoint의 응답 형식을 Legacy compatible과 Standard 중 하나로
  결정하고, 계약을 변경할 때는 클라이언트와 합의한 뒤 명세를 갱신하도록 규정한다. 그러나 레거시에 동일한
  endpoint가 없다면 보존할 기존 응답 형식 자체가 없다. 따라서 해당 경우에 대한 분류 기준을 마련해야 한다.
  초안 결정 3의 필드 제거가 해당 규칙의 적용 대상인지 확인한 뒤 처리 방식을 확정한다.

- 초안 결정 7은 MOM-0851에서 `workspace` 모듈 root에 `WorkspaceReader`를 먼저 추가한 뒤 다시 검토한다.
  [첫 웹 read 슬라이스 계약](../design/legacy-product-api-migration-workspace-read-design.md)에서도 웹
  워크스페이스 조회를 위한 public API로 같은 이름을 사용하지만, 반환 타입은 `WorkspaceDetail`이며 단건 조회
  메서드는 `Optional`을 반환한다. 모듈 경계에 대한 판단은 이번 결정과 같지만, 구체적인 조회 계약은 다르다.
  bootstrap은 워크스페이스 id 집합으로 여러 건을 조회하며, 결과에서 `id`와 `name`만 사용한다. 따라서 이번
  결정은 MOM-0851에서 추가한 `WorkspaceReader`에 목록 조회 메서드를 확장하는 형태가 된다. 조회 목적에 따라
  결과 record를 분리할지, `WorkspaceDetail` 하나로 통합할지는 MOM-0851 구현 시점에 함께 확정한다.

- 초안 결정 3은 `momens-server`가 아직 prod 환경에서 모바일 트래픽을 받지 않는다는 전제를 바탕으로 한다. 이 전제는
  앱을 배포하는 것만으로 해소되지 않으며, MOM-0840을 통해 prod 환경에서 스키마 반영이 완료되어야 한다. 그 이후에
  같은 유형의 필드를 제거하려면 ADR-0006에 따라 v2 API를 도입해야 한다.

- 결정 2는 모든 리소스가 프로젝트 id 또는 태스크 id로 접근 가능하다는 전제에 기반한다. 워크스페이스가 조회
  대상이 되는 화면이 생길 경우 재검토가 필요하다.

- 결정 1은 기기 간 선택 상태 동기화가 제품 요구사항이 아니라는 전제를 바탕으로 한다.

- 워크스페이스와 프로젝트 사이에 팀 계층이 추가되면 현재의 `projects` 구조가 변경될 수 있다. Linear처럼
  워크스페이스와 프로젝트 사이에 team 레이어를 두는 구조가 일반적이기 때문에, 조직 규모가 커질 경우 동일한 요구가
  발생할 가능성을 염두해야 한다.
