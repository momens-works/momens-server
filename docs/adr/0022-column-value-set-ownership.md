# 0022. 컬럼 허용 값의 관리 기준과 도메인 enum의 역할

- 상태: Proposed
- 날짜: 2026-09-06
- 작성자: jsshin8128

## 맥락

DB 컬럼의 허용 값 집합이 여러 위치에 중복 정의되어 있습니다. `tasks.status`의 다섯 가지 값은 Flyway 마이그레이션의 CHECK 제약, project 모듈의 `TaskStatus`, mobile 모듈의 `BoardStatus`와 요청 검증용 `@Pattern`, web 모듈의 `TaskWriteService.normalizeStatus`에 각각 선언되어 있습니다. `MOM-0884`에서 CHECK 제약과 enum을 비교해 불일치를 탐지하는 테스트를 추가했지만, 값 집합을 어디에서 관리하고 각 모듈이 표시 순서, 기본값, 레거시 입력 별칭 같은 부가 정보를 어떻게 관리할지는 정해지지 않았습니다.

이 문제를 결정하려면 다음 세 가지 조건을 고려해야 합니다.

첫째, `momens-api`와 `momens-worker`도 공유 DB에 데이터를 기록합니다. 따라서 Java enum은 해당 enum을 사용하는 서버의 쓰기 경로에만 제약을 적용하며, 모든 쓰기 주체에 동일하게 적용되지는 않습니다.

둘째, ADR-0019에 따라 이 서버가 공유 DB의 DDL을 관리합니다. 따라서 CHECK 제약은 이 레포지토리의 Flyway 마이그레이션을 통해서만 변경할 수 있습니다.

셋째, `ddl-auto=validate`는 CHECK 제약을 검증하지 않습니다. 따라서 DB 제약과 코드가 일치하지 않아도 애플리케이션 기동 시점에는 문제가 드러나지 않습니다.

CHECK 제약과 enum의 값 집합이 의도적으로 다른 경우도 있습니다. `workspace_invitations.role`의 CHECK 제약은 `owner`를 허용하지 않지만, `WorkspaceRole`에는 `owner`가 포함되어 있습니다. 초대를 통해 `owner` 역할을 부여할 수 없다는 규칙은 `isAssignable()`로 표현합니다. 따라서 값 집합 관리 규칙은 이러한 의도적인 차이까지 설명할 수 있어야 합니다.

## 결정

**허용 값 집합의 기준은 공유 DB의 CHECK 제약으로 정합니다. 값 집합은 이 레포지토리의 Flyway 마이그레이션을 통해서만 변경합니다.** PostgreSQL의 CHECK 제약은 행을 삽입하거나 갱신할 때 적용됩니다. 따라서 어느 서버가 데이터를 기록하더라도 동일한 조건이 적용됩니다. 세 쓰기 주체에 모두 적용되는 선언은 CHECK 제약뿐이며, 이를 변경할 수 있는 곳도 이 레포지토리가 유일합니다.

허용 값 집합에는 `NULL`을 포함하지 않습니다. 컬럼의 `NULL` 허용 여부는 컬럼 정의에서 별도로 정합니다. PostgreSQL의 CHECK 제약은 검사 결과가 `NULL`이면 제약 위반으로 처리하지 않고 통과시킵니다.

도메인 enum은 컬럼을 기준으로 관리합니다. 테이블을 관리하는 모듈에는 컬럼별로 해당 값 집합을 표현하는 도메인 enum을 하나만 둡니다. 여러 컬럼이 같은 값 집합을 사용하더라도 CHECK 제약은 컬럼마다 적용되므로 각 컬럼에 대응하는 도메인 enum을 별도로 둡니다. 도메인 enum은 해당 개념에서 사용할 수 있는 값과 각 값에 적용되는 비즈니스 규칙을 관리합니다.

**표시 순서와 라벨, 저장된 값의 해석 방식, 레거시 입력 별칭은 mobile과 web 모듈이 관리합니다.** 이러한 정보는 화면 설계나 레거시 API 호환 범위에 따라 변경되므로, 허용 값 집합과는 변경 사유가 다릅니다.

하지만 mobile과 web 모듈은 값 집합을 별도로 다시 선언하지 말고 도메인 enum을 참조해야 합니다. 만약 특정 모듈에서 허용해야 하는 값의 범위가 도메인 enum보다 좁다면, 해당 모듈에 별도의 enum을 정의할 수 있습니다. 이 경우 요청 검증도 모듈의 enum을 기준으로 수행합니다. 기본값은 제품 전체에서 동일하게 사용한다면 도메인에서 관리합니다. 반대로 클라이언트마다 기본값이 다르면 도메인에서 기본값을 정하지 않고, 클라이언트가 해당 값을 필수로 전달하도록 합니다.

**값 집합은 확장한 뒤 축소하는 순서로 변경합니다.** CHECK 제약의 허용 값 집합은 어느 시점에도 이 서버에서 기록할 수 있는 값 집합을 포함해야 합니다.

값을 추가할 때는 마이그레이션, 도메인 enum, `CheckConstraintEnumLinks`, mobile, web 모듈을 같은 PR에서 함께 변경합니다. Flyway가 애플리케이션 기동 전에 실행되므로 CHECK 제약이 먼저 확장됩니다.

값을 제거할 때는 먼저 쓰기 경로에서 해당 값을 제거하고, 기존 데이터를 정리한 뒤 CHECK 제약을 축소합니다.

**`MOM-0884`에서 추가한 테스트는 등록 의무와 값 집합의 일치 여부를 강제합니다.** 값 집합을 제한하는 CHECK 제약이 `CheckConstraintEnumLinks`에 등록되지 않았거나, 연결된 enum의 값 집합이 선언된 차이와 일치하지 않으면 테스트가 실패합니다. 컬럼별로 도메인 enum을 하나만 두는 원칙과 mobile·web 모듈이 값 집합을 중복 선언하지 않는 규칙은 테스트로 검출할 수 없으므로 리뷰에서 확인합니다. 상시 적용할 규칙은 `docs/rules/persistence.md`의 「값 집합」 소절에 기록합니다.

## 대안

**도메인 enum을 기준으로 CHECK 제약을 생성하는 방안은 채택하지 않았습니다.** Hibernate 6는 `@Enumerated(STRING)`이 적용된 컬럼의 스키마를 생성할 때 CHECK 제약도 함께 생성합니다. 그러나 이 레포지토리에서는 Flyway가 스키마를 관리하고 Hibernate는 `validate`만 수행합니다. 또한 값 집합이 의도적으로 다른 다섯 가지 사례에서는 생성 결과가 올바르지 않습니다. 도메인 enum 역시 해당 enum을 사용하는 서버의 쓰기 경로에만 제약을 적용합니다.

**CHECK 제약을 기준으로 enum을 생성하는 방안도 채택하지 않았습니다.** 생성된 enum으로는 표시 순서, 라벨, 권한 서열을 표현할 수 없습니다. 또한 모바일 priority처럼 컬럼의 허용 값보다 좁은 값 집합도 표현할 수 없습니다.

**PostgreSQL ENUM 타입, DOMAIN 타입 또는 조회 테이블을 사용하는 방안도 채택하지 않았습니다.** 이러한 방식은 기존 컬럼 타입을 변경해야 하며, 컬럼 타입 변경은 이번 작업의 범위에 포함되지 않습니다.

## 결과

값을 추가하거나 제거할 때 각 선언을 변경하는 순서가 명확해집니다. 다른 쓰기 주체에서 새로운 값을 기록해야 한다면 이 레포지토리에 CHECK 제약 변경을 요청해야 합니다. `momens-proto` 계약과 CHECK 제약 간 정합성은 이 결정의 범위에 포함하지 않습니다.

결정에 어긋나는 선언을 전수 조사한 결과, `tasks.status`, `tasks.priority`, `tasks.role`은 아직 이 결정을 따르지 않고 있습니다. project 모듈은 세 값을 도메인 enum으로 검증하지 않으며, mobile·web·minsu 모듈은 값 집합을 문자열로 중복 선언하고 있습니다. `projects.health_status`, `milestones.health_status`, `task_updates.kind`도 web 모듈의 OpenAPI 설명과 엔티티 기본값에서 허용 값을 다시 선언하고 있습니다.

결정에 어긋나는 선언은 후속 구현 티켓 MOM-0949에서 모듈 구분 없이 정리합니다.
